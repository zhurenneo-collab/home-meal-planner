# 今天吃什么 · 家庭中餐菜单规划器 V1

无需服务器的家庭中餐菜单规划页面。直接用浏览器打开 `index.html` 即可使用；菜单、菜品设置、周预览缓存、点菜订单和历史记录保存在当前浏览器的 `localStorage` 中。

## 使用方法

1. 打开 `index.html`，页面会显示本周工作日菜单。日期选择器可调整菜单周一；“生成下一周”推进7天，“生成未来4周”生成20个工作日。
2. 刷新或再次打开时，页面会按本机日期定位到本周；本周预览会从本地缓存恢复。过去/未来周的预览也会保留，选回对应周一日期即可恢复。用每道菜旁的替换按钮更换菜品，用锁按钮锁定单道菜或整天。重新生成时会保留锁定内容；若锁定冲突或菜品库不足，页面提示原因并保留原菜单。
3. 确认后点“保存菜单”。保存记录按日期更新；重复保存部分日期不会删除其他日期。保存的菜单会进入最近菜单及去重历史，预览不会进入历史。
4. 可复制单日菜单、本周菜单和按天整理的采购清单。采购清单合并食材名称，不估算重量。
5. 使用左侧边栏（手机端为底部导航）切换“菜单页 / 点菜页”。点菜页沿用菜单页的卡片与留白风格，左侧分类栏可切换菜品类别，也可按关键词搜索带生成图片的菜品；调整份数、填写日期与备注后即可提交；订单仅保存在本机；点菜页的“下单历史”可新增或删除整张订单，并为订单增减菜品份数。刷新后会回到上次打开的主页面。旧的 `order.html` 会自动跳转到集成后的点菜页。
6. 在“菜品库”里编辑菜品、收藏或排除菜品、新增及删除自定义菜品。内置菜品不能删除；已被当前菜单或已保存菜单引用的自定义菜品不能删除。
7. 点“导出数据”保存 JSON 备份；“导入”会先校验文件并在替换前备份当前数据。菜单预览缓存、上次打开的页面和本地点菜订单也会随 JSON 导出。数据不会自动跨设备同步。

## 稳定性与数据安全

- 生成、替换、保存和导入共用确定性的菜单规则校验。生成器使用有界回溯；菜品库足够时，同一份5日或20日菜单内荤菜、素菜、汤品分别不重复。某一类可用菜少于菜单天数时，只对该类放宽单品去重；找不到完整合规方案时会失败，不会返回部分菜单或绕过规则。
- 锁定约束在重新生成和替换时都会复核。单道菜替换还会检查前后工作日的主蛋白轮换。
- 保存记录以日期为准，同一天再次保存会更新该日期。最近菜单展示最新保存批次；较早的其他日期记录继续保留。
- 首次读取旧版数据时，会在迁移前复制原始存储到 `home-meal-planner-v1-backup-before-schema-3-*`。若安全备份或本地写入失败，页面会阻止覆盖并提示。导入会在写入前创建独立备份。
- 菜品名称、食材和制作提示在页面输出时转义；导入会校验结构和字段。导入失败不会替换现有数据。

## 说明

- 每份热量是按常见食材参考值与默认份量粗略估算的约值，不是营养分析或医疗建议。
- 图片为内嵌生成图片，离线可显示。内置菜品和图片内容保持不变；菜单页和点菜页共用同一菜品图片并可离线运行。
- 项目文件：`index.html`（唯一的桌面与手机响应式入口；点菜页已并入）、`rules.md`（规则和存储说明）。
- 生成结果是家常搭配建议。过敏或忌口食材应在菜品库排除，并在烹饪前再次确认。

## GitHub Pages 与手机使用

当前统一入口是 `index.html`，同一套响应式页面适配电脑与 iPhone；不再单独维护手机版副本。仓库内的 `.github/workflows/pages.yml` 使用 GitHub 官方 Pages Actions，在推送到 `main` 后自动部署；部署只发布入口页面和图标/manifest 资源。仓库首次启用时，在 GitHub 仓库的 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。

本项目已部署在公开仓库，源码、菜品数据和内嵌生成图片都可被公众查看。正式网址是 `https://zhurenneo-collab.github.io/home-meal-planner/`。项目不含后端密钥；当前检查未发现 API key、token、私钥或环境配置文件。`.github/workflows/pages.yml` 会在推送到 `main` 后通过 GitHub Actions 更新站点。

在 iPhone 上用 Safari 打开 HTTPS 网站，点“分享”→“添加到主屏幕”；可选择“作为 Web App 打开”。本页包含 iOS Web App 元数据、主屏幕图标和轻量 manifest，不依赖 PWA 框架。相关选项以当前 iOS/Safari 版本为准。

**本地数据不会随网站发布或同步。** Safari 与电脑上的浏览器分别保存自己的 localStorage，访问 GitHub Pages 的新域名也不会继承本地 `file://` 或其他域名中的数据。请先在旧浏览器导出 JSON，再在新网址导入；之后刷新或重新打开同一域名可读取该浏览器中保存的数据。不同设备仍需各自导入备份。

不要提交 `.env`、令牌、私钥或个人本地配置；`.gitignore` 已忽略常见敏感配置文件。


## 多设备同步（Supabase）

线上版本支持多个设备使用同一个邮箱验证码登录，云端同步菜单、菜品偏好、已确认菜单、点菜订单和历史。未登录时仍可离线使用；本机数据继续写入浏览器 localStorage。不同设备的浏览器数据互相独立。

### 配置与部署

1. 在 Supabase 创建免费项目，在 Dashboard 的 SQL Editor 执行仓库中的 `supabase.sql`。脚本建立每账号一行的数据表，并启用 RLS；普通匿名访问不能读取菜单数据。
2. 在 Supabase 的 Authentication > URL Configuration 配置允许的站点地址（GitHub Pages 地址），并按需配置 Email OTP。
3. 部署工作流会把公开的 Project URL 和 publishable key 注入 GitHub Pages 构建产物；离线版可在 `index.html` 中配置这两个常量。publishable key 本来就会公开给浏览器使用。**不要使用或提交 service_role/secret key。**
4. 提交并推送到 `main`，GitHub Pages 工作流会重新部署。访问页面点“多设备同步”，使用同一邮箱分别登录各设备。
5. 首次登录若本机与云端都有数据，页面会要求选择保留哪一份；覆盖本机前会自动备份当前 localStorage 数据。可随时使用“导出数据”再额外保存 JSON 备份。

云端按账号隔离且目前采用整份应用状态同步。设备处于离线状态时，本机操作仍可用；重新联网后自动尝试同步。若两台设备同时修改，页面会提示选择数据来源，避免静默覆盖。登录会话保存在各设备本机，不包含在 JSON 导出中。


订单历史中的“添加菜品”会进入选菜页面，并带入原订单的日期、备注和已选菜品。确认后更新原订单，保留原下单时间，不会额外创建重复订单。
